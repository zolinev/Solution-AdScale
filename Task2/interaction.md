#Проектирование взаимодействия

###Определите протоколы и паттерны взаимодействия

Различные протоколы подбираем исходя из бизнес-процесса и требований к нагрузке:  
вызовы от B2B Gateway API к Bidding Service и от B2C Gateway API к Delivery Service - строго gRPC в потоковом режиме в силу высокой транзакционной нагрузки и высоких требований latency

Для цепочки вызовов от Dashboard Gateway API к Adertiser Dashboard, от Adertiser Dashboard к PaymentService, от PaymentService к Платежному Шлюзу допустимо использование REST в силу требований обязательной синхронности (нельзя отпустить клиента, не проведя платеж или не выдав ошибку) и небольшой нагрузки

Для всех остальных взаимодействий между сервисами необходимо использовать Кафку, так как 

1. Инициирующему сервису по бизнес-смыслу нет необходимости дожидаться обработки события вызываемым сервисом и тратить на это ресурсы
2. На одни и те же события могут подписываться разные сервисы и в случае неиспользования Кафки нам бы пришлось делать дополнительные вызовы из каждого сервиса еще к N сервисам

###API Gateway нужен?
Считаю API Gateway обязателен.

В целевом виде предлагаю сделать три отдельных сервиса - каждый под свою группу потребителей, чтобы исключить взаимное влияние.

Реализовывать предлагаю на Envoy Proxy, в силу его легковесности, скорости и продвинутой поддерже rate limiting. DevOps-инженеры в команде есть, разворачивание не должно стать проблемой

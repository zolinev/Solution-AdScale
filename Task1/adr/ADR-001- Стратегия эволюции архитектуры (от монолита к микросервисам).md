# ADR-001: Стратегия эволюции архитектуры (от монолита к микросервисам)

**Дата:** 2026-06-10

**Статус:** Предложено

## Контекст

AdSacle готовится к интеграции с крупной DSP-площадкой. В горизонте 3х месяцев ожидается рост нагрузки на 20%, через год - двукратное увеличение нагрузки с пиковой нагрузкой до 50000 RPS против текущих 15000. Наиболее нагруженный функционал - проведение аукциона. 
На текущий момент все ИС реализована как модульный монолит с муодулями на разных языках (C++, Node.js, Go, Python) без возможности масштабировать отдельные компоненты. База данных - одна инсталляция PostgreSQL без read-реплики.
Уже на текущий нагрузках есть проблемы с производительностью - SLA P95 - 120мс, при необходимых 100мс. 
Новый DSP-партнер накладывает жесткие требования к SLA - P95 < 80мс, в случае невыполнения SLA или downtime компания AdScale будет вынуждена платить штрафы.


Ключевые архитектурные драйверы:
- Нагрузка: 50K RPS в пике, P95 задержка < 80 ms
- Доступность: SLA 99,99%
- Сроки: 3 месяца до запуска интеграции с DSP-площадкой. Год - до двукратного роста
- Команда: 35 человек. Backend-, frontend- и DevOps-разработчики, тестировщики, дизайнеры, сотрудники службы поддержки и менеджмент
- DevOps: CI/CD есть, Kubernetes нет
- Документация: нет

Рассматривались три альтернативы:

1. Оставить монолит как есть, добавить read-реплики Postgre
2. Максимально быстрый переход на микросервисы
3. Плавный переход на микросервисы (выполнение пункта 1 к моменту интеграции с DSP-площадкой и последующая миграция на микросервисы в течение года)

### Альтернатива 1: Монолит остается, добавляем к Postgre read-реплику
Плюсы: минимальные изменения, быстрый time-to-market, уберем основные конкуренции на БД. 
Минусы: остается одна БД - в случае отказа полная недоступность системы.  Не можем масштабировать функционал выборочно - только увеличение мощности железа под всем монолитом.


### Альтернатива 2: Максимально быстрый переход на микросервисы
Плюсы: четкие границы модулей, отстутствие конкуренции за ресурсы, возможность горизонтального масштабирования. Минимизация трудозатрат разработчиков на переход
Минусы: риски при проведении регресса из-за отсутствия документации на ИС, риски простоя системы при внедрении, невозможность реализации в 3х месячный срок до интеграции с DSP-площадкой


### Альтернатива 3: Плавный переход
Плюсы: в конечном итоге такие же как у варианта 2. В промежуточных состояниях - минимазация рисков простоя системы, минимизация ущерба в случае критических ошибок из-за возможности отката на монолит.
Минусы: усложнение разработки из-за реализациции рубильников для отката, усложнение тестирования из-за необходимости постоянных проверок "по-старому" и "по-новому", часть промежуточных решений, принятых в процессе перехода, может не понадобится в целевом решении


## Решение

Стратегия эволюции архитектуры (от монолита к микросервисам): плавный перехой
- в течение 3х месяцев (к моменту интеграции с DSP-площадкой) необходимо создать read-реплику для БД
- в течение года
	- реализовать переход на микросервисы, соблюдая принцип «База данных для каждого сервиса»
	-  для хранения статистики и построения отчетов использовать ClickHouse. В Postgre эти данные не хранить
	-  для работы высоконагруженных модулей (auctionService, DeliveryService) использовать кеш Redis
	-  синхронные вызовы между сервисами использовать только в случаях, когда это продиктовано объективной необходимостью (например, проведение платежа или аукциона), во всех остальных случаях использовать асинхронное взаимодействие через Kafka

## Последствия

**Положительные:**
- Обеспечиваем достаточный SLA к моменту интгерации с DSP-площадкой
- В целевом состоянии ИС готова к нагрузке 50K RPS и готова горизонтально масштабировать при росте потребностей бизнеса

**Отрицательные:**
- Существенные трудозатраты на реализацию целевого решения
- Увеличенные затраты команды разработки на переходный период
- В проможетучном состоянии в случае деградации БД имеем риск выйти за SLA и платить штрафы 

 
**Риски:**
- если после добавления read-реплики по-прежнему останется бутылочным горлышком то разделить БД на две: кампании+финансы, и статистика+аналитика
- возможно потребуется усиление devops-команды

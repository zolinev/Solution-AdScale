#Отказоустойчивость данных

###RPO и RTO для каждого сервиса

- слой севрисов Gateway API - RPO не применим - RTO секунды
- Bidding Service - RPO не применим - RTO секунды
- Delivery Service - RPO не применим - RTO секунды
- Advertiser Dashboard - не применим - RTO часы
- Campaign Service - не применим - RTO минуты
- Payment Service - не применим - RTO минуты
- Financial Service - не применим - RTO секунды (в случае, если у рекламодателя закончился бюджет, а его банеры выигрывают в аукционе будем оплачивать мы сами)
- Statistics Service - не применим - RTO минуты/часы
- Analytics Serviсe - не применим - RTO минуты/часы
- Cachе Actuator Service - не применим - RTO - секунды

- Кеш Redis - RPO минуты (запустим прогрев кеша, отработаем на fallback-стратегиях ) - RTO минуты
- БД Статистики ClickHouse - RPO 0 (недопустима потеря статистики, иначе у клиентов отчеты не сойдутся с финансами) - RTO минуты/часы
- БД Кампаний - RPO 0 (недопустима потеря информации об изменениях кампаний) - RTO минуты
- БД Финансов - RPO 0 (недопустима потеря финансовой информации) - RTO секунды (в случае недоступности БД финансов потеряем актуальность балансов, начнем показывать рекламу, на которую нет бюджета)

#стратегия резервного копирования
- БД Финансов и БД:
	- снимаем полные бэкапы раз в сутки. 
	- Настраиваем потоковую репликацию, таким образом всегда имеем полный WAL-журнал и обеспечиваем RPO 0
- БД Статистики (ClickHouse):
	- полный бэкап раз в неделю  
	- инкрементельный бэкар раз в день
	- последние часы в рамках дня докатываем за счет сдвига офсета в Кафке
- Кеш Redis - резервного копирования нет, всегда можем восстановить через прогрев кеша

#соответствие принципам 12-факторных приложений.
Все создаваемые сервисы должны создаваться в соответствии с принципом 12-факторных приложений:

- Кодовая база - запрещено иметь разные ветки кода под разные серверы (тест, НТ, ПРОД)
- Зависимости - Явно указать все зависимости в манифестах, таких как requirements.txt или pom.xml, и автоматизировать их установку при развёртывании.
- Конфигурация - все параметры передаем через переменные окружения
- Сторонние службы - сторонние службы подключаются как внешние ресурсы
- Сборка, выпуск, запуск - Процесс сборки, выпуска и запуска должен быть разделён на отдельные стадии
- Процессы - все сервисы должны быть Stateless
- Порт привязки - все сервисы должны быть самодостаточным и не зависеть от внешнего веб-сервера
- Конкурентные процессы - сервисы должны масштабироваться путём запуска многих потоков
- Утилизируемость- сервисы должны быть лёгкими для запуска и остановки
- Среды разработки и эксплуатации - среда разработки должна максимально приближаться к среде эксплуатации
- Логи - сервисы должны писать свои логи в стандартный вывод
- Административные процессы - административные задачи должны выполняться как одноразовые процессы
